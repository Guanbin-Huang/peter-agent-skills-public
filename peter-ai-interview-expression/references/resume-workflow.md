# A｜简历怎么写：融合 ASu 的岗位定位与经历重组

本流程改编自 ASu 的 `great-resume`、`job-match` 及主张—证据账本；精确来源与许可见 [第三方说明](../THIRD_PARTY_NOTICES.md)。本功能可独立执行，不要求另装 ASu。

## 1. 确认输入，不先替用户选一个虚构岗位

读取目标 JD 或明确的岗位方向、原简历、项目/工作材料、个人职责与结果证据。缺完整 JD 时按明确方向给草稿，不猜公司硬门槛；最多列 5 项关键待补。用户只要一个 bullet 或短开场时直接做这一项。

## 2. 对照岗位要求，分开表达缺口和真实缺口

先列硬门槛，再列技术/业务/协作要求；为每项建立“JD要求—现有证据—状态—行动”矩阵。状态只用已匹配、表达缺口、证据不足、真实缺口、待确认。材料没有出现不等于用户不会；在明确事实前保持待确认，不报伪精确匹配百分比。按主技能的 `project_domain` 选择 Agent 或具身技术口径，不能把仿真、真机、算法与部署成果混写。

## 3. 建事实底稿与定位

强主张、指标冲突、多岗位版本或 A→B 交接时维护 [主张—证据账本](claim-evidence-ledger.md)；简单短文案不强制建文件。输出 1–3 个岗位定位，可区分稳妥与进取；进取定位必须说明缺什么证据。保持正式职位、公司、时间、教育背景真实。

## 4. 把底层动作翻译为招聘方可理解的表达

按“动作 → 系统能力 → 业务价值 → 结果证据 → 个人边界”组织简历。一般条目可压为“场景/任务 + 本人动作与取舍 + 可核验结果”。技术栈只保留与动作有关的词，不能用关键词堆砌替代贡献。使用主导/负责人等动词前核对决策、交付和结果；团队结果与本人实现分别写。

优先交付：一句话定位、顶部摘要、2–4 条项目/经历 bullet、改写前后与事实依据；按需要附 HR 开场白（约 80–160 字）和最多 5 项补证。非实测数字标测算，原型/试点/生产与计划分别说；只有 loss 下降、HTTP 200 或感谢消息不写成项目已成功。

## 5. 回读和向 B 交接

逐条检查“原始说法—建议写法—证据—个人边界—待确认”；数字、版本、职责与日期在所有产物一致。已确认主张不能继续带待补占位；来源冲突不选择更有利的一版。需要项目文档/面试稿时按 claim ID 传同一底稿到 B，让每个强亮点都能展开具体事件、决策、取舍及验证。

仅读过外部论文时可以写调研/学习，不写成亲自设计、部署或取得作者指标。已有可用的外部排版/投递 skill 可以按明确需求交接；本包先完成文本内容，不冒称 HTML/PDF、网页填写、自动投递已完成。

## 最小例子（教学设定，不是使用者经历）

原始材料：“团队做了客服 Agent；我只负责检索评测，记录了失败样本，但没有线上数据。”

可用 bullet：“负责客服 Agent 的检索评测，记录并整理评测中出现的失败样本，为后续分析提供依据；线上效果待验证。”

B 的追问：“你怎么定义失败样本？怎样比较两种检索方案？这项评测由谁实现？”不能把这一条升级成“主导整个客服系统上线”。
