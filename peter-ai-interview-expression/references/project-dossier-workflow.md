# 项目档案证据与维度

## 从真实工作到剧本

先按 [面试剧本流程](real-work-interview-script.md) 整理角色、事件、矛盾、选择和现有结果；原始事实、当时判断与事后复盘分别记录。档案服务表达，不为追求结构完整制造经历。事实明确后，继续提炼工作价值与可追问节点。

## 证据结构

C01 是一句可检查的主张；E01 是某人的经历或实验凭据；S01 是外部论文、代码或讨论。编号在本项目稳定，新增不重新排列旧编号。

- E 记录主体、原始出处/文件位置、日期、具体行为、原话或短摘、验证状态。聊天还记录 talker/local_id（可得时）和转发层级；录音记录时间段。只保留必要个人信息。
- S 记录标题/作者、直接链接、读取日期、论文版本或仓库 commit/tag、已读范围、支持的 C、适用条件与反例。不要只贴平台首页。
- 主张支持状态区分：本人自述、有材料支持、本轮执行验证、推断、待补。声明“本轮执行验证”必须有真实命令/输入/输出或外部系统回读。
- 接受冲突而不擅自消除：同时列不同版本、说话人和时间。需要当事人确认的事实不靠网络推测。

## 学习状态（逐项标记，不是一条自动晋级的阶梯）

| 状态 | 可支撑的说法 | 需要的证据 |
|---|---|---|
| 阅读/理解 | 我阅读、比较或解释了什么 | 来源、关键结论、自己的解释与边界 |
| 跑通 baseline | 我在某环境跑通某命令 | 固定版本、环境、日志、输出 |
| 复现 | 我按某设置复现了某结果 | 数据/配置、评估协议、对照、偏差；跑通不等于复现论文指标 |
| 修改实验 | 我改了什么并做了对比 | diff、变量、对照条件、实验记录 |
| 集成/部署 | 我连接了哪些组件 | 接口、端到端运行、闭环结果；仿真与真机分别标记 |
| 实际责任 | 我负责、协作或决策什么 | 职责描述、协作记录、交付/验收；学习状态不能推出工作职级 |

## 技术维度：只展开当前主线

Agent：用户任务→输入 schema→规划/状态→工具参数→调用结果→状态变更→任务验收。选最相关的超时、重试、幂等、权限、评估或成本延迟解释；工具返回成功不等于用户任务完成。

VLA 微调：观测图像/本体状态/语言→数据转换与时间对齐→动作表示及归一化→权重/冻结/训练配置→离线评估→闭环执行。检查相机视角、action chunk、控制频率、延迟及执行接口是否与训练约定一致。loss 下降不等于闭环成功率提升。环境依赖、OOM、NaN、梯度与冻结、数据泄漏、抖动分别定位，不混成“模型效果不好”。真机动作试验遵守设备文档与用户授权，不把论坛猜测直接用于硬件。

每条主线回答：输入是什么（字段/shape/单位/坐标系按需）→哪个组件变换→输出给谁→哪里可能失效→用什么观察验证。不知道的实现细节标待查，不用通用架构填成该项目的事实。

## 非技术维度

| 维度 | 问题 | 有价值的材料 |
|---|---|---|
| 价值/场景 | 谁遇到什么问题，为什么值得做，为什么不是更简单方案 | 需求、用户反馈、业务基线；无实测 ROI 就列假设 |
| 角色/责任 | 谁提出、谁决策、谁实现、谁验收；我参与哪部分 | 职责和协作记录，而非部门名称列表 |
| 资源/取舍 | 时间、算力、数据、人手、供应商、预算如何影响方案 | 排期、约束、方案对照、变更记录 |
| 协作/交付 | 上下游接口和依赖如何对齐，变更如何传递 | 接口约定、会议结论、交付清单 |
| 验收/复盘 | 如何判定成功、谁确认、失败怎样处理 | 测试与验收记录、遗留问题和复盘 |

脑图只是候选检查清单，不是本人全部掌握的证明；选择相关模块并标已覆盖、待补、不适用。

## Bug 卡和补证任务

Bug 卡：现象与期望 → repo/commit、依赖、硬件、配置 → 最小输入与复现命令 → 候选原因 → 区分假设的实验与实际输出 → 根因证据 → 修改 → 同条件前后结果 → 回归范围 → 当前状态（线索/已复现/已定位/已修复待回归/已验证）。没有执行就写“建议验证”，不伪造日志。

社区点赞、感谢、关闭 Issue 都不等于当前版本修复。核对相关 PR 是否合并、是否发布、自己装的版本是否包含。无法确认时保留未知。

补证任务最多五项，按“影响口述真实性→影响项目判断→补充背景”排序。每项含当前缺口、最小行动、可观察验收和需要谁提供什么；不要给没有材料支撑的完成时间承诺。
