## 增量审核：两条即开工，结尾单条自动处理

**用户体验**：你继续往后看，我同时改前面；已确认无问题的部分复用，修改处单独复查，最后统一合成。以下是新项目/后续执行的规则；现有回调是否已接入自动调度，必须实查，不由本文代替实现。

### 1. 修改自动启动，最终批准仍需用户确认

- 保存 Comment 就是修改对应片段的指令，满两条立刻启动；不要求另外点“已审到这里”。确认审片范围只用于最终合成验收，不作为局部修改的前置条件。
- 用项目级 `incremental_review_state.json` 保存 `basePreviewSha256`、`baseEdlHash`、`reviewedRanges`、`reviewComplete` 和确认来源/时间；每个已审区间保存原版 Preview 范围及对应 `sourceRanges`。初始 `reviewComplete=false`，只有用户明确全片审完才更新。
- 没有 Comment、播放头越过某点、局部修改块全通过，都不代表未看部分通过。用户明确要求先改某个范围时可先做，但不因此扩大已审范围。

### 2. 每两条自动开始，结尾剩一条自动处理

- 待处理集合仅计已保存、有评论文字、未解决且尚未消费的批注版本。每个版本用 `markerId + 内容指纹` 标识；指纹包含评论文字、范围、全局/局部和源映射，不用整份文件的 `updatedAt` 判定新批注。
- 空闲时每保存两条立即启动，无 5 秒防抖。忙时新 Comment 持久化进待处理集合，当前批结束自动取两条；播放到结尾自动处理剩余一条，结尾新保存的单条也自动处理，回退播放位置恢复两条触发，不依赖浏览器轮询、手动提交或标记已审。未保存草稿不入队；保存不等于确认全片。
- 每批保存独立的评论、时间线、映射和规则快照，记录 `batchId`、`markerRevisions`、`basePreviewSha256`、`baseEdlHash`、状态及产物。明确的手动 `E/A/S/D` 时间线操作也必须入账，优先于 AI 删改；即使只有一条评论，也不得遗失或遗漏在最终合成之外。
- 合并重叠/相邻语义范围后再分工；两个评论可能是一份任务。完整词句跨出默认窗口时遵守双窗口规范，记录最小扩展，不能为了并行切断话意。

### 3. 并行只发生在独立局部

| 修改 | 可提前做的事 | 主执行者必须负责的事 |
|---|---|---|
| 不改时长的 B-roll、动效、字幕改字 | 独立制作局部低清样片；音轨复用 | 冻结共享视觉规则、校验后合入唯一 manifest |
| 删气口/删句、调顺序、变速 | 分析原声/词级 timing、准备局部 edit proposal | 合并冲突，唯一源 EDL 提交，按同一 keeps/倍速重建音画和字词映射 |
| 重叠批注或全局规则 | 读取完整上下文，准备一个合并方案 | 暂停受影响任务的提交，更新规则版本，重新计算依赖后再派发 |

- 当前运行时维持一个主协调执行器自动接续，每批两条；每个局部任务只写自己的批次/板块目录，不共写 `review_edit_plan.json`、ASS/SRT、B-roll manifest、活动评论或发布页面。只保留一个主调度/合成写者，机器负载高时降低编码并发，不牺牲正在播放的审核页。
- 合成坐标以原片文件 ID/哈希、真实 PTS 区间、源 EDL 段落实例 ID 为锚；同一素材重复出现时实例必须可区分。`previewTime` 只用于定位所看的版本，不能把旧版秒数直接用于删过内容的新版。
- 用户审核期间不热替换当前媒体、不清空活动 `preview_comments.json`。新片段在逐块审核页单独展示；切换整体版本时显式迁移源映射并保留旧版和批注。

### 4. 返修、缓存和失败恢复

- 批次状态：`queued → running → ready_for_review → approved`；运行失败记 `failed`，输入过期记 `stale`。批次状态与板块 `pending / approved / changes_requested` 分开保存；渲染完成不等于用户通过。旧版本被新版本取代后记 `superseded` 并记录 `replacedBy`；撤回项记 `cancelled` 并保存撤回证据。历史记录保留，但全片闸门只检查当前有效版本的未决任务。
- 运行中新增独立批注进入下一批；旧评论被编辑/撤回或其输入改变时，取消排队版本，运行版本标 `stale`。提交结果前再次比对评论版本与依赖；旧任务即使后来成功也不得覆盖新结果。
- 指纹至少含源素材、原片区间/段落实例、局部 edit、输入倍速、编码参数、字幕/图层依赖和规则版本。只要实际影响该块的依赖变化，旧缓存/审批失效；远处删句只改变输出位置且本块内容不变时，允许重映射并复用，仍核对新接缝。
- 全局样式修改单独保存 `globalReviews[{ruleHash,scope,sampleHash,status}]`，先生成代表性低清样片供确认，再重做受影响图层；受影响板块的旧视觉审批失效。内容未变的已审区间保留内容确认，但不代表新样式已经通过；全局调整若改变内容、顺序或切点，则撤销受影响区间的内容确认。全局样式没有局部批注时也必须产生审核对象，不得绕过验收。
- 只重做过期/失败部分，不重跑全量 ASR、不重复压缩已通过主体。失败批次保留真实日志、原版本和活动评论；修正原因后以同一逻辑批次幂等重试，避免重复应用删改。

### 5. 局部验收和最终合成

- 局部完成就按后文流程一展示独立约 10 秒片段，用户只检查修改处及邻接语境，不必从头重看每一批。合并修改的片段覆盖完整语义，约 10 秒不是硬截断。
- **CHECKPOINT**：全片明确审完 + 最新批注/手动时间线变更都有处理记录 + 当前有效版本无 queued/running/stale/failed/冲突待处理项 + 所有修改块及全局样式审核对象 approved，四项齐备才进入完整低清版；前一分钟的 2/2 approved 不满足全片闸门。已 superseded/cancelled 的历史任务不阻塞新版本，但必须能回溯到替代版本或撤回证据。
- 唯一主执行者从原片与冻结源 EDL 合成；不拼各自带音频、各自变速的低清审核小片。纯画面修改复用当前音频母版；结构变化按同一源 EDL 同步重建视频和音频母版，避免逐块 AAC 编码延迟累计。
- 延续 v2 的源 PTS → 变速 → 真正 fps 重采样 → 整数帧规则。复用视频段需匹配参数/时基，先按帧数合并画面，再与统一音频母版封装；有跨边界图层时同时重做邻段。
- 核对变更块首/中/尾的原片画面/音频映射、全部新接缝、完整解码、字幕映射，以及播放器实际媒体哈希/Range。总时长相等或 ASR 对齐不单独构成口型同步证明。高清仍等最终确认后按成片路径输出。

### 6. 接入验收：规则不冒充已上线功能

- 先读实际页面、服务和队列代码。`codex_callback.js` 现为两条自动启动、结尾单条处理的自动队列；原有全部板块通过检查不包含全片已审范围。保留其单写者约束，不能通过去掉运行锁来实现并行。
- 若当前页未接入增量队列，由主会话从已落盘的批注和时间线建立独立批次并执行局部任务，向用户说明“流程已更新，自动触发尚未接入”；不要临时替换活动评论来骗过全量回调，也不宣称页面已自动开工。
- 真正上线自动模式时验证：两条立即启动且只启动一次；积压按两条自动接续，结尾一条自动处理；编辑旧评论使旧结果失效；新批注不断流；刷新/重启可恢复队列且不重复执行；结尾单条自动处理；同区不并发提交；审核未覆盖全片时拒绝完整输出；当前媒体不被替换。测试通过再启用，并提供暂停/继续入口。

## 一、三个不同概念

| 概念 | 时间范围 | 用途 |
|---|---:|---|
| M 点 | 精确到当前播放时间 | 批注锚点，不代表自动切点 |
| 回顾窗口 | `M-6 秒 ～ M+4 秒` | 听原声、读逐字稿、理解前因后果 |
| 处理窗口 | `M-3 秒 ～ M+3 秒` | 批注默认要求执行修改的区域 |

回顾窗口和处理窗口都不是“整段自动删除”的范围。回顾窗口是判断依据，处理窗口是默认 edit 边界；真正入点、出点必须保护字头字尾、天然气口和完整语义。

## 二、标准处理顺序

1. 以 M 点建立回顾窗口和处理窗口，并分别映射到原片；跨 Preview 拼接点时保留多个原片区间。
2. 先完整试听回顾窗口，同时读取该 10 秒对应的词级逐字稿。
3. 结合用户评论，判断处理窗口里究竟是删重复、缩气口、修异常声音，还是保留不动。
4. 回到原片时间线，以词级时间戳和实际听感确定切点；不要在已经剪过的 Preview 上继续逐点叠加碎切。
5. 相邻批注的回顾或处理窗口重叠时，先合并理解，再从原片重建一次，避免同一区域产生连续跳切和孤立静音碎片。

原则上只改处理窗口。若一个完整字词或句义边界刚好跨出处理窗口，不得为守住秒数而截断语音；允许贴近边界做最小扩展，但处理记录必须说明原因。

## 三、处理数据包

每条批注至少包含：

- 精确 `previewTime` 和 `sourceTime`
- `reviewPreviewStart/reviewPreviewEnd/reviewSourceRanges`
- `actionPreviewStart/actionPreviewEnd/actionSourceRanges`
- 回顾窗口对应的词级 `transcriptSegments`
- 分类、用户评论、处理状态
- `scopeMode`：`local`（非全局）或 `global`（全局检查）

### 全局检查开关

- 默认是 `local`。按一次 `G` 切换为 `global`，再按一次恢复 `local`；页面必须提供可点击的同等按钮。
- `global` 仍保存 M 点、回顾窗口和处理窗口，但三者只作定位锚点，不限制最终处理位置。
- 生成处理包时，`global` 批注必须附带完整逐字稿和全片 source ranges，并明确要求检查前后重复、论证顺序和可移动位置。
- 全局检查的结果可以是删除、修改建议或调整到其他位置；不得只在 M 点附近机械剪切。

生成命令：

```bash
node "$SKILL_DIR/scripts/build_preview_edit_packets.js" \
  "$REVIEW_DIR/preview_comments.json" \
  "$REVIEW_DIR/preview_review_config.json" \
  "/path/to/subtitles_words.json" \
  "$REVIEW_DIR/preview_edit_packets.json"
```

执行者必须先读 `reviewWindow.transcriptSegments`，再设计 `actionWindow` 内的 edit。

## 四、页面交互基线

- `Space`：只切换播放/暂停。
- `M`：先暂停，再在精确当前时间打点并聚焦评论框。
- `G`：在“非全局 / 全局检查”之间切换；输入法组词期间不得抢占按键。
- 新批注的分类默认选中中性的“其他”；只有用户主动选择后，才把“这里短一点”等分类作为剪辑意图传递。
- 评论框 `Enter`：保存；`Shift+Enter`：换行。
- 保存或取消后，焦点返回可响应视频快捷键的区域。
- 时间轴用白线显示 M 点、蓝色显示回顾窗口、橙色显示处理窗口。

### 剪映式试剪时间线

页面底部同时提供一条非破坏性试剪时间线：

- `E`：在播放头处分割当前片段，内容不变。
- `A`：删除当前片段左边缘到播放头的部分。
- `S`：删除播放头到当前片段右边缘的部分。
- `D`：删除当前选中的整个片段；未手动选择时使用播放头所在片段。
- `Command/Ctrl + Z`：撤销上一步。

试剪轴必须像剪映一样把保留片段自动吸附排列，播放时自动跨过被裁掉区间；同时保留一条原始 Preview 总览轴，标出裁掉区域。所有操作写入 `preview_timeline.json`，不得直接覆盖 Preview 视频。

`preview_timeline.json` 中的片段时间仍是 Preview 时间。生成 `preview_edit_packets.json` 时，脚本必须把它们映射成 `manualTimeline.sourceKeeps`；正式视频从原片重建，不能二次编码 Preview。用户用 `E/A/S/D` 做出的明确试剪，优先于 AI 的自动删减建议。

## 五、示例

当 `M = 00:12.3`：

- 回顾窗口：`00:06.3–00:16.3`
- 处理窗口：`00:09.3–00:15.3`

正确做法是先听和读 `00:06.3–00:16.3` 的完整语境，再只针对 `00:09.3–00:15.3` 附近的问题确定精确切点。

## 六、验收

- 页面、JSON、处理数据包中的两个窗口一致。
- M 点精确保留，不被窗口起止时间替代。
- 处理数据包包含回顾逐字稿和两套原片映射。
- 不出现吞字、连气口过紧、孤立静音碎片或同一区域多次叠加跳切。
- 新 Preview 从原片重建并默认保留或按当前时间线重建规范字幕；只有用户本次明确要求“无字幕”时才跳过。字幕调用 `douyin-captions`，保持正式版纵横比与字幕视觉占比，优先验证听感、逻辑连贯性和字幕同步。
- `E/A/S/D`、撤销、自动保存和磁吸播放全部可用，刷新页面后试剪片段仍在。

## 七、一键回调 Codex

Preview 页面可以把已保存的批注直接交给独立 Codex 精剪执行器，不再要求用户复制清单：

1. 每次保存 Comment 时，先完成当前评论框的保存，并确认 `preview_comments.json` 与 `preview_timeline.json` 都已成功落盘；任一保存失败都不得启动精剪。
2. 桌面版会持有当前任务的唯一 writer，后台不得再执行 `codex exec resume <thread-id>` 与其双写。固定启动 `codex exec --ephemeral` 独立执行器；禁止用 `--last` 猜测任务。只要本机 Codex CLI 可用即可启用自动修改。
3. 回调 prompt 只引用项目目录、评论 JSON、时间线 JSON、配置和处理包等真实文件，不把浏览器显示文字重新拼成未经验证的剪辑命令。全局批注仍必须先读取完整逐字稿并检查全片结构。
4. 服务只监听 `127.0.0.1`；每个审核目录生成随机回调令牌，提交接口只接受 JSON 和正确令牌，同一时刻只允许一个主调度任务运行；它分派的局部子任务只写独立目录，不得并发启动多个全量回调。配置、prompt、日志和状态内部文件不得经静态文件路由公开。
5. 页面持续轮询，但将内部状态翻译为“正在修改 / 等待处理 / 已改好 / 需检查”。运行中解析 Codex JSONL 事件，只展示脱敏的人话进度：明确上报的 `进度 X/4`、已运行时长、当前动作、最近更新时间和最近 5 条活动；禁止用定时器虚构百分比。超过 1 分钟没有新事件时标成“多久前更新”，同时用 PID 存活状态区分“长命令仍在运行”和“进程已退出”。执行完成后直接在页面展示执行器的最后回复；新 Preview 使用独立版本审核页，保留活动评论和已提交快照；不清空用户仍在编辑的批注，也不在原播放器热替换媒体。失败时优先展示日志里的真实错误，不只显示退出码。


## 七-A、自动增量批处理运行时

1. 保存批注后，页面不再要求人工复制清单；服务端按 `id + contentHash` 追踪 fresh marker，空闲时满两条立即冻结并启动，繁忙时积压后每批两条，结尾余一条自动处理。
2. 批次冻结即生成 `codex_batches/<batchId>/batch.json`、本批 `comments.json`、`timeline.json`、`preview_review_config.json`；执行器只读取这些快照，不读取活动批注作为本批输入。
3. `preview_review_config.previewVideo` 是 `basePreviewSha256` 的来源；不得用不存在的 `preview.mp4` 代替当前播放器文件。
4. 旧批次在批注删除、resolved、编辑或内容哈希变化后统一标 `stale`；即使 worker 后来成功返回，也不得覆盖新版状态。
5. 失败批次保持 held，不自动无限重试；修改批注后形成新版本再处理；失败或过期批次不阻塞后面的有效 Comment。
6. `codex exec --ephemeral` 只输出到本批目录：局部 review clips、proposal、结果页和 QA。禁止改活动 `preview_review.html`、`preview_review_config.json`、`preview_comments.json`、播放器视频、共享 EDL，禁止从局部结果直接生成流程二完整视频。
7. 完成判定必须同时满足：worker 退出成功、结构化 result JSON 可解析、每个 batch marker 都有 item、且至少一个真实存在的 `outputFile/outputPreview/resultPage`。
8. 页面移除“已审到这里”“立即处理当前批次”，仅显示人话状态和可选暂停/继续。保存先落盘试剪时间线，再落盘 Comment并自动调度；已完成结果保持可查看，播放器不热替换。整片批准仍按流程二闸门验收。

## 八、批注重剪的两阶段交付

每批局部修改完成后立即进入流程一，不等后续批注收齐；不直接交付一条拼接 Review 视频，也不立刻生成完整成片。固定分成两个流程：

1. **流程一：逐块审核 HTML**
   - 每条批注对应一个独立审核板块，不把所有片段拼成一条视频。
   - 每块播放该批注修改完成后的局部结果，默认保留修改点前 5 秒、后 5 秒；靠近片头或片尾时向另一侧补足为约 10 秒。
   - `ArrowRight` 表示当前板块通过并进入下一个；`ArrowLeft` 返回上一个。
   - `M` 在当前审核片段的精确时间暂停并填写 Comment；`Enter` 保存为“需要再改”，`Shift+Enter` 换行。
   - 每块独立保存 `pending / approved / changes_requested`、评论及片段内时间点，刷新页面不得丢失。
2. **流程二：完整视频**
   - 只有全片明确审完、所有最新批注/手动变更已处理、队列无未决任务且流程一所有修改板块为 `approved`，才允许基于同一份原片时间线生成完整 Preview。
   - 任一板块仍为待审核或需要再改时，禁止先输出新的完整视频。

流程一可用 `scripts/build_annotation_block_review.js` 从原片、最新批注和精确 edit decision 生成；页面和状态默认写入 `annotation_block_review.html`、`review_clips/`、`review_blocks.json`。

## 九、返修状态机

每个独立板块固定使用以下状态：

```text
pending ──右方向键──> approved
pending ──M + Comment + Enter──> changes_requested
changes_requested ──重新剪辑──> pending
approved ──片段内容发生变化──> pending
```

执行规则：

1. `review_blocks.json` 是流程一板块审核状态的唯一事实源。板块内返修读取 `status`、`reviewerComment`、`reviewerCommentTime` 和 `reviewedAt`；不要假设 Comment 存在 `comments[]` 或 `reviewComments[]`。初始 M 批注另读 `preview_comments.json` 的 marker 版本；增量批次与全局样式审核另读 `incremental_review_state.json`，不要混用三个层次。
2. 原有生成器的板块指纹覆盖 `sourceRanges` 和 `editSummary`；主执行者还必须按增量规则核对素材、速度、渲染和字幕/图层依赖指纹。任何影响实际内容的依赖改变，旧 `approved` 都必须失效为 `pending`；不能因旧脚本只比较两个字段而放过全局样式变化。
3. 返修后保留原 `reviewerComment`，让用户明确知道本轮修的是什么；清空 `reviewedAt`，并增加 `revision`。
4. 只返修一条时，使用 `build_annotation_block_review.js` 的第 5 个参数传序号，例如末尾加 `4`；不要重渲染全部 15 条。
5. 页面刷新后自动定位到第一条未通过的板块。用户在聊天里明确确认唯一待审核返修“修复好了”时，可把该条写为 `approved`；多个未完成项存在时必须逐条确认。

## 十、从原片生成流程二

主执行者先检查全片已审、最新批注/手动变更已处理及队列清空，流程一再达到 `N/N approved` 后，执行（脚本的 approved 检查不能替代前述全片闸门）：

```bash
node "$SKILL_DIR/scripts/render_approved_full_preview.js" \
  "/path/to/source.mp4" \
  "$REVIEW_DIR/review_edit_plan.json" \
  "$REVIEW_DIR/review_blocks.json" \
  "/path/to/流程二完整低清.mp4"
```

渲染器必须满足：

- 先核对增量审核完成条件，再校验所有板块均为 `approved`；`pending` 或 `changes_requested` 任一存在即退出。
- 使用 `review_edit_plan.json.keeps` 从原片一次重建，不从 Review clip 或旧 Preview 二次编码。
- 视频和音频应用同一倍速；低清 Preview 默认 270×480、30fps、H.264 + AAC，并保留或重建规范字幕。1080×1920 基准为 76px，其他分辨率按 7.04% 画面宽度同比缩放字号、位置、阴影和安全边距；得意黑、白字、柔和黑影、无描边。只有用户本次明确要求“无字幕”时才跳过。
- 每个剪辑段音频接缝只做 5ms 级极短淡入淡出，避免孤立爆音；视频保持硬切。
- 手机素材按真实源 PTS 定位，先变速、再真正重采样至 CFR 30fps，逐段使用整数帧。复用/拼接的视频段必须匹配编码参数和时基，再与统一音频母版封装；不直接拼独立编码的带音频审核块。不能只比较 avg_frame_rate 来推断同步。

## 十一、交付验收

流程二交付前固定检查：

1. 全片已审、最新批注/手动变更已处理、无未决任务，且 `review_blocks.json` 显示 `N/N approved`。
2. `ffmpeg -v error -i output.mp4 -f null -` 从头到尾无错误。
3. `ffprobe` 显示 30fps，视频/音频都存在，音画时长差小于 100ms。
4. 保留整片首/中/尾的方向、画幅与内容抽检；另核对变更块首/中/尾的实际原片画面与音频映射、所有新接缝和字幕。运行 v2 源时序检查与 `verify_served_media.py`，确认播放器媒体哈希及 Range。前三项不单独构成口型同步证明。
5. 报告输出路径、时长、分辨率、体积、倍速、字幕状态和审核通过数。

### 反模式黑名单

- 不把所有修改片段拼成一条 Review 视频；流程一必须逐块导航。
- 不因用户说“整体搞定”就忽略已有 `reviewerComment`；先读真实状态。
- 不在返修后沿用旧 `approved`。
- 不在流程一未 100% 通过时抢跑流程二。
- 不从低清 Preview 二次剪流程二。
- 不只看文件存在或总时长相等就宣称同步；必须核对实际源音画映射、接缝、完整解码和网页媒体。
- 不把尚未查看的部分默认为通过，不以局部 2/2 approved 提前生成整片。
- 不覆盖活动批注、不让过期任务覆盖新结果、不去掉全量回调运行锁来假装并行。
